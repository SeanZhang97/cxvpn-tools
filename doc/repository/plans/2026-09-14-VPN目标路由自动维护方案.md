# VPN 目标路由自动维护方案

日期：2026-09-14 | 分支：main | 状态：用户已批准实施，代码与离线、原生路由验证完成；真实网页验收受 VPN 会话异常阻断

## 目标与验收条件

用户配置 `chaoxing.com → 孙河机房ikev2` 后，首次访问此前未出现的子域名，或 DNS
返回新的服务器地址时，软件自动确保所选 VPN 到真实目标 IP 的可达路由。
用户无需枚举子域名、维护 IP 清单或反复重连 VPN。

必须满足：首次连接前完成路由准备；保留物理与订阅出口；保护用户原有路由；VPN 不可用时
保持原出口选择并明确失败；TUN 和 system-proxy 都有确定行为。

## 实施前核实的基线

1. `core/routing.py::_target_vpns` 收集配置引用的 VPN。
2. `build_mihomo_config` 为每个 VPN 生成 `VPN-n` direct 出口并设置 `interface-name`，
   域名规则指向该出口；PHYSICAL 和订阅节点绑定物理接口。
3. Mihomo v1.19.30 的 `adapter/outbound/direct.go` 调用自己的 DNS resolver 与 dialer。
   `component/dialer/dialer.go::parseAddr` 得到真实 IP，再逐个或并发进入 `dialContext`。
4. Windows `component/dialer/bind_windows.go` 使用 `IP_UNICAST_IF` / `IPV6_UNICAST_IF`
   指定接口，不创建 Windows 路由。该调用链与 Controller 路由表未提供面向本软件的
   “准备目标路由后再连接”配置接口。
5. Rust `RuntimeManager` 管理预检、应用、commit/rollback、启停和崩溃恢复，尚无目标路由管理。
   当前 IPC 版本为 6、服务版本为 0.7.0；普通服务请求处理持有 manager 锁。
6. 现有离线测试验证配置与接口绑定，不能证明新域名第一次真实访问成功。

当前手工修复的 6 条 office `/32` 路由和原 `45.113.20.0/24` 继续作为用户原有路由保留，
不得在升级中自动删除或认领。

## 方案选择

| 路径 | 收益 | 问题与取舍 |
|---|---|---|
| 周期解析已知域名 | 不修改核心 | 后缀不能枚举所有子域名；与核心 DNS 缓存可能不同；不能保证首次访问 |
| 监听失败日志后补路由 | 易与现有日志接入 | 请求已经失败；日志不是可靠控制协议，不作为正式方案 |
| VPN 增加高 metric 默认路由 | 无需跟踪 DNS，范围较小的代码调整 | 引入覆盖所有目的地址的候选默认路由，影响默认路由检测及故障时出口选择；不能未经真实隔离验证宣称等价于精确分流 |
| 本地 SOCKS 转发层 | 可在连接前准备路由 | 新增 TCP/UDP 数据面与协议维护，违背现有 Mihomo 单一数据面设计 |
| 为固定版本 Mihomo 增加受管 VPN 连接钩子 | 使用实际连接 IP，覆盖首次访问，保留现有 DNS/数据面 | 需要维护最小上游补丁、定制核心构建和服务协议；本方案推荐，但必须先确认核心定制 |

不新增独立 DNS 代理，不维护另一套 DNS 缓存。DNS 仍由 Mihomo 按现有配置解析；路由依据
核心实际准备使用的 IP 申请，覆盖 CNAME、多 A/AAAA、缓存命中及并发连接候选。

## 推荐实现

以下方案已实施。当前服务为 0.8.0、控制 IPC 7，固定核心为 v1.19.30-cxvpn.1；
当前调用链、资源上限及异常边界见 [VPN 目标路由自动维护知识库](../knowledge/modules/VPN目标路由自动维护.md)。
原生 API 原型已验证 TUN 与物理保护路由的接口隔离。生命周期测试同时发现并修正了
`InitializeIpForwardEntry` 默认自动配置标记与严格回读不一致的问题。

### 连接前准备

链路：原域名规则 → 受管 VPN direct → Mihomo 解析目标 → 请求本机路由服务 →
服务确认真实接口及目标路由 → 核心绑定接口并连接 → 连接关闭释放租约。

- 在固定 v1.19.30 基础上维护显式启用的受管 VPN 能力，仅生成给配置引用的 VPN direct；
  普通 direct、PHYSICAL、订阅节点和核心自身 DNS 不启用此能力。
- TCP 钩子放在最终真实 IP 确定后、实际 socket connect/TFO 前；每个并发候选独立申请租约。
  失败、取消、竞速落败都释放租约，成功租约随连接关闭释放。
- UDP 在实际目标确定后、创建/使用出站 socket 前准备路由；必须覆盖后续目标变化和
  PacketConn 复用，不能只在首次 ListenPacket 时检查一次。
- ICMP 不沿用未实现的 TCP/UDP 承诺；验收明确本期域名分流支持的流量范围。
- 核心启动回报能力版本；生成受管 VPN 配置前检查能力，不能让官方旧核心静默忽略新字段。

### 原生服务与权限

- 路由请求使用独立受限 Named Pipe，不挤占现有控制 IPC 的 8 个连接槽或 manager 主锁。
  初始边界：单次准备 2 秒总期限，最多 32 个并发准备、4096 个受管路由项；满额明确失败。
- 服务以当前应用配置及核心进程世代维护允许的 VPN 标识；客户端不允许提交任意接口、网段、
  网关、metric 或 shell 命令。使用客户端 PID、实际子进程身份及世代校验，不能只相信请求字段。
- 目标只接受单个规范化 IPv4/IPv6 地址；排除 fake-IP、回环、组播、未指定地址及不适用的
  链路本地地址。内部业务地址可以通过 VPN，但优先复用已有覆盖路由。
- 服务自行解析接口 LUID、当前连接状态和地址族；使用 IP Helper API 查询和修改活动路由。
  不向 VPN 电话簿持续追加历史地址，不要求重连 VPN，不运行逐请求 PowerShell。
- 已有有效路由只复用不认领；新增条目记录精确身份与所有权，事务失败只清理本次创建项。

### 路由选择及副作用门控

精确 `/32` 或 `/128` 仍是 Windows 系统路由，前缀比 TUN 通常的覆盖路由更具体。
因此不能仅添加 VPN host route 就宣称不影响其它流量：未绑定接口的 IP 直连可能绕过 TUN。

实现前先进行可回退的隔离原型验证：

- TUN 模式：评估同时维护相同前缀、优先级更高的 TUN 接管路由，使未绑定连接继续进入
  Mihomo；VPN socket 通过接口绑定选择 VPN 对应条目。确认不会递归，并覆盖多 VPN 同 IP。
- system-proxy 模式：确认未经代理的连接仍沿原有效物理路径，而代理内部绑定 VPN 的
  socket 使用 VPN 路径；如需保护路由，必须复用真实网关并跟随物理网卡变化。
- 原型无法证明上述隔离时，停止进入正式实现，更新方案；不得退回全隧道或静默绕过 TUN。
- VPN 缺少可用 IPv6 地址时不创建虚假 IPv6 路由；由既有核心地址族候选机制选择可用 IPv4，
  AAAA-only 请求明确失败，不回退物理出口。

### 生命周期、并发与恢复

- 路由以接口 LUID、地址族和目标 IP 为键，多个域名/连接共享计数；不同 VPN 不能混用。
  新请求即时回查实际路由，不只依赖内存缓存。
- DNS TTL 控制解析缓存，不直接决定删除活动路由。新 DNS 结果自动请求新 IP；旧 IP 在
  无活动连接后保留 60 秒空闲宽限再回收，避免长连接因 DNS 到期被切断。
- 状态绑定核心世代，关闭及取消可靠释放；进程死亡和服务恢复时清理其孤儿记录。
  先写恢复意图，再创建路由，再确认结果，启动时对中断记录逐项回读；外部修改过的条目
  不按旧记录强删。
- VPN 重连使用新接口事实；新连接重新准备，旧世代请求不再创建路由。VPN 掉线不改出口。
- 配置变更/rollback 关联原有事务：新配置失败时还原旧策略，保留仍有效旧连接租约；
  不立即删除旧配置中仍被活动连接使用的路由。
- worker、队列、取消和定时回收独立于服务主循环；外部调用有超时/失效结果检查。

### 日志与界面

日志记录申请、领取、开始、复用/创建、失败/超时/取消、释放和清理，关联请求及核心世代。
只记录 VPN 标识、必要的目标 IP/端口和错误类型，不记录 URL 查询参数、凭据、Cookie。
已有正常路径只记录状态变化与限频汇总；界面保留原有规则交互，仅沿现有失败通道返回必要提示。

## 验证顺序与门槛

1. 隔离 Windows 原型：验证受约束接口上的目标路由以及未命中流量不改出口；失败则停下修订。
2. 离线测试：首次冷域名、多 IP、IPv6 不可用、DNS 变化、同 IP 多 VPN、并发取消、长连接、
   容量上限、已有路由保护、路由被外部删除、接口重连、进程崩溃恢复、配置 rollback。
3. 协议测试：错误客户端、伪造 VPN、过期世代、无效目标、超时与队列满均明确拒绝，
   控制状态查询和关闭仍能及时响应。
4. 编码覆盖：中文、组合字符、非 BMP VPN 名与异常日志，UTF-8 IPC 和落盘不退回系统代码页。
5. 编译和构建最小模块；真实网络验证不以离线测试替代。
6. 经用户确认真实验证范围后：office 已知域名与此前未访问且有真实 DNS 的超星子域名，
   冷启动首次访问、VPN 断开重连、物理/订阅出口回归和 IP 直连不绕过 TUN。
   `mooc.chaoxing.com` 是否存在及提供何种服务需届时实测，不能预设其必然可访问。
7. 全部门槛通过后按项目规则打包、核对真实桌面主库与配置、启动新版；服务升级可能触发 UAC。

## 失败与回退

开发阶段保持现有运行配置。保存原版核心及摘要，只在原型与离线门槛通过后替换验证产物。
部署失败或真实隔离门槛不通过，停止新核心、清理确认归属本任务且无活动租约的路由，
恢复原核心与原服务并回读用户配置；保留已有手工 office 路由保证当前已恢复链路。
任何清理/恢复不确定均保留证据并明确失败，不报告成功。

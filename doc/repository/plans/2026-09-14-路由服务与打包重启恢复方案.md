# 路由服务与打包重启恢复方案

日期：2026-09-14
分支：main（工作区）

## 背景与已验证事实

- Wi-Fi 切换到网线后，旧运行配置仍固定绑定 `WLAN`，启用代理首先被物理接口校验拒绝。
- `CXVPNRoutingService` 随后长期停留在 `START_PENDING`；现有安装器等待停止超时后仍继续覆盖
  `CXVPNRoutingHost.exe`，最终因旧进程占用文件报 `os error 32`。代理启用和域名分流保存共用
  `Api._apply_routing_locked -> RoutingManager.apply` 原子提交链，因此服务事务失败时配置不会落盘。
- 本机同时存在安装目录 1.2.0 与工作区 `dist` 1.2.1。启动日志出现
  `second instance blocked, restored=True`，说明新产物可能只唤醒旧进程而未真正运行。
- 权威用户配置位于 `%LOCALAPPDATA%\CXVPNTools\state.sqlite3`；`config.json` 是兼容导出。
  现有旧数据迁移仍可能按修改时间用旧便携配置覆盖 LocalAppData 的兼容文件，边界过宽。
- 设置页原先把页面启动时取得的整份 `CFG` 回传给通用保存接口。页面快照过期或来自旧前端时，
  保存单个开关也可能连带覆盖账号、凭据、自动化和模型字段；单份 `.bak` 又会被后续保存滚动覆盖。
- 本次明确不处理网络抓包及运行日志脱敏。

## 调用链与修改方案

### 1. 路由服务异常恢复

调用链：

`UI apply_routing/set_routing_enabled`
→ `Api._apply_routing_locked`
→ `RoutingManager.apply`
→ `core.routing_service` 提权安装
→ `routing-service/src/installer.rs`

修改：

- 将服务停止/删除改为可失败的受检操作。
- 正常停止超时后，从 `sc queryex` 的当前服务记录解析精确 PID；仅对该 PID 执行强制终止。
- 强制终止后再次确认服务已停止，再执行删除，并确认 SCM 已不再返回该服务。
- 任一确认失败时停止安装，不覆盖仍被占用的服务文件；回滚仍保留旧服务恢复尝试。
- 自动物理出口复核遇到服务 IPC 暂不可用或服务在锁等待期间消失时按未就绪处理，清除候选并等待
  下一轮，不再因对空状态调用 `.get()` 产生每 60 秒一次的 `AttributeError`。

### 2. LocalAppData 与开机启动入口

调用链：

`main.py` 启动前迁移
→ `core.app_paths.migrate_legacy_user_data`
→ `Api -> core.config.load -> core.state_store.load_config`

修改：

- 当目标目录已有 `state.sqlite3` 时，将其视为已经建立的权威存储；旧安装目录或 `_internal`
  中的 `config.json` 只保存冲突副本，不再覆盖 LocalAppData 当前兼容导出。
- 开机启动注册表已有 `CXVPNTools` 项时，保留“已启用”语义，但将命令校正为当前 EXE 的绝对路径；
  同时继续清理旧产品名入口。

### 3. 打包重启闭环

调用链：

`build.py/build_protected.py`
→ 关闭运行实例
→ 构建原生服务与 PyInstaller 产物
→ 核对用户配置
→ 启动新产物

修改：

- 两种构建入口复用一个小型生命周期模块；只处理明确的 CXVPNTools 新旧进程名。
- 构建开始前强制结束并限时等待实例完全退出，避免文件锁与单实例锁残留。
- 停止实例后读取 SQLite 中配置 revision/payload 摘要及兼容 JSON 摘要；构建完成、启动前再次核对。
- 停止前记录正在运行的新旧程序精确安装目录，停止后也把这些目录纳入便携数据迁移，避免只扫描
  当前工作区 `dist` 而遗漏实际被终止的旧安装副本。
- 构建前通过 SQLite backup API 保存完整一致性副本并限制保留数量，不单独复制主文件遗漏 WAL。
- 仅启动本次生成的 `dist/CXVPNTools/CXVPNTools.exe`，并确认实际进程路径匹配；失败则构建流程报错。

### 4. 启动时第三方代理保护

调用链：

`Api.start_background_tasks`
→ `Api._start_routing_standby_reconcile`
→ `routing.windows_system_proxy`

修改：

- 持久化配置为启用且系统代理关闭时，仍允许恢复 CXVPN 接管。
- 系统代理已指向非当前 CXVPN mixed-port 时，视为用户已切换到 Clash Verge 等其它代理；记录状态后
  直接结束启动复核，不调用快速开关、完整路由应用或 Codex 代理同步。
- 用户在界面中主动点击启用 CXVPN 时，继续按明确操作执行接管；本保护只约束应用启动时的自动恢复。

### 5. 配置字段级提交与恢复历史

- 设置页每次只提交本次操作拥有的字段 patch，不再回传页面缓存的整份 `CFG`。
- 后端拒绝包含 `creds`、`credential_status`、`authorization` 或 `routing` 的通用保存请求；这些字段
  只能由各自专用业务链更新，旧缓存页面最多保存失败，不能清空权威配置。
- 覆盖 `config.json` 兼容导出前，在 `config-history` 保存上一完整版本并滚动保留 20 份；SQLite 仍是
  主提交点，历史文件仅用于误操作后的人工恢复。

## 失败与恢复边界

- 服务 PID 缺失、PID 强杀失败、服务未停止或未删除：终止新服务覆盖，保留可定位错误；不按进程名
  扩大终止范围到无关系统进程。
- 用户配置摘要变化：停止自动启动新产物，保留 LocalAppData 原文件和迁移冲突备份供恢复。
- 新 EXE 未启动或实际路径不匹配：报告失败，不把旧窗口可见或同名旧进程视为成功。
- 构建失败：不启动半成品；LocalAppData 不作为 PyInstaller 清理目标。
- 启动时存在第三方代理：保留系统当前值，不用持久化的 CXVPN 开启状态覆盖用户刚完成的代理选择。
- 旧页面提交整份配置：拒绝请求并保留当前数据库；不得为了兼容旧页面继续接受覆盖式写入。

## 验证计划

- Python：旧便携配置较新但目标已有 `state.sqlite3` 时不得覆盖；当前启动项路径自动校正；打包生命周期
  的进程等待、完整 SQLite 备份、配置摘要和路径确认使用模拟测试；字段级设置提交不得覆盖凭据；
  第三方系统代理存在时不得触发 CXVPN 自动接管。
- Rust：`sc queryex` 状态/PID 解析、停止与运行状态判断的纯逻辑测试；执行
  `cargo test --offline --manifest-path routing-service/Cargo.toml`。
- 项目离线回归：执行与路由、用户数据迁移、桌面启动和构建规则直接相关的测试。
- 打包：执行 `uv run --with pyinstaller python build.py`。核对 LocalAppData 配置摘要未变化、产物
  时间戳更新、实际运行进程路径指向新 `dist`。
- 运行恢复：核对 `CXVPNRoutingService` 不再停留 `START_PENDING`，CXVPN 的 mixed-port/controller
  进入监听；再应用自动物理接口配置并确认域名分流可以提交。该步骤不修改日志脱敏逻辑。

# 代理启停状态收敛方案

- 日期：2026-09-16
- 分支：main
- 授权：用户要求优化并开启子智能体审查；不执行真实代理启停，最终由用户手动验证。
- 本轮不打包、不重启 GUI 或服务，避免改变当前运行状态；既有知识文档改动保留。

## 已确认调用链与问题

首页开关和域名分流保存共同进入 `Api._apply_routing_locked` → `RoutingManager.apply`。
TUN 关闭先停止运行时、恢复代理快照、刷新当前用户设置，然后后台复核再次调用完整关闭流程，
启动待机核心。原样保存仍会进入停止与重建。所有配置提交受同一 `_routing_lock` 保护。

原生事务通过 `apply` 启动候选 → Python 验证 → `commit`；失败走 `rollback`。
现有 Controller 等待不检查核心退出；原生 status 会清空退出进程，抢走 tick 的清理依据。
诊断只取回滚后末尾日志，可能丢失候选失败现场。Windows 手动代理空地址或冒号在恢复快照
中已有归一化，但当前用户刷新后缺少核对，启动门控仍把冒号当作合法第三方代理。

## 实现边界

1. 仅对已开启且服务器为空或冒号的无效手动代理，在当前用户 WinINet LAN 设置中关闭手动
   代理并清空服务器。保留 PAC、自动检测、绕过列表和命名 VPN 连接；先备份、复核、再写入和回读。
   合法第三方代理继续保留/拒绝覆盖，preview 不产生修复副作用。
2. 关闭成功后核对当前用户最终状态；已关闭且运行配置匹配、核心健康的 standby 直接复用。
   不能仅凭已保存配置相同跳过运行态确认。子智能体复核确认：stopped 不代表路由/代理快照清理
   成功，因此未运行核心仍保留原生幂等 stop/刷新，用于重试异常清理；本轮不新增清理状态协议。
3. Controller 就绪等待同步读取原生运行状态，核心退出立即失败；保留原有就绪总期限。
   原生 status 不清掉退出证据，记录 PID/退出码，在 rollback 前保存失败日志，沿用既有 IPC 字段。
4. 快切补写启用位必须确认地址仍是本次本机端口；回退失败明确报告。启动恢复统一经过已有
   配置/网卡校验。提交成功后的缓存维护异常不得误报事务失败或阻断待机任务。
5. 两位子智能体分别审查 Python 与 Rust 启停边界；仅纳入已证实、与本次状态收敛直接相关的问题。

## 风险与恢复

- Windows 状态可能被其它软件同时修改；修复前再次核对，合法端点或其它字段变化则停止修复，
  不无条件清除系统代理。备份失败、WinINet 写入/回读失败不报告修复成功。
- 无效地址来源和此前 Mihomo 退出的根因尚不确定；不宣称消除所有驱动或外部进程故障。
- 保留配置提交失败时恢复原配置与服务事务回滚边界；诊断和维护失败不能遮蔽原始错误。
- 代码可按本次 diff 回退，用户数据不迁移、不修改。未运行新代码，不改变当前网络。

## 最小验证与人工验收

- Python 离线模拟覆盖无效地址修复、合法代理保留、回读失败、无变化保存复用、配置变化重建、
  已停止核心仍重试异常清理、核心退出提前失败、快切补写/恢复失败、提交后维护异常。
- Rust 单元测试覆盖退出观测不丢证据、失败日志跨 rollback 保留及审查确认的必要事务约束。
  不启动 Mihomo，不访问真实注册表、Named Pipe、网络或 Windows 服务；每组测试最多 60 秒。
- 语法、相关 UI 静态检查（仅有 UI 改动时）、diff 检查；不运行全量集成或真实流量测试。
- 后续用户在部署新版后手动验证：TUN 开→关→开；关闭后原样保存；system-proxy 快切；合法第三方
  代理恢复；失败提示与日志。文档记录本轮离线通过项及未部署边界。

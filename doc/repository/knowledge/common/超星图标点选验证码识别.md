# 超星图标点选验证码识别

模块: 通用能力 | 代码路径: `core/captcha_handler.py`、`core/web_flow.py`
最后验证: 2026-08-28 | 分支: 非 Git 工作区

## 当前事实

- 站点: `https://remote.chaoxing.com/vpn`；验证码类型 iconclick，弹窗容器 `#eject`，
  主图容器 `#cx_imgBg`（background-image 为 sprite），刷新按钮 `.cx_refresh`。
- **连败失败态（2026-08-27 实测）**: 连续点错后站点把弹窗底部换成
  「失败过多，点此重试」横幅, 此时 `.cx_refresh` 无效, 必须点横幅才
  重置出新图。captcha_handler._click_retry_if_blocked (text=点此重试
  检测+点击) 已接入 _refresh 与 attempt/人工循环顶部 (先复位再取图)。
- sprite 结构（320x240 JPEG，2026-08-26 实测并经人工确认）:
  上 160px 为主图，图标坐标 1:1；主图图标为实心带内部镂空样式，
  可能是白色或黑色版本，尺寸约 20~45px。
  底部 80px 为**四排指令区**（每排高 20px）:
  - 行1 (y160-180): 黑图标白底，**左→右即真实点击顺序**
  - 行2 (y180-200): 同组黑图标，**行1 的反序**（干扰）
  - 行3 (y200-220): 白图标黑底，顺序同行1
  - 行4 (y220-240): 同组白图标，行3 的反序（干扰）
  即每个目标图标在 sprite 内有黑/白各 2 个共 4 个渲染（12~20px），
  均远小于主图图标（约 1.5~2.5 倍尺度差）。
- sprite CDN（captcha-b.chaoxing.com）直链需请求头
  `Referer: https://remote.chaoxing.com/`，否则 403。
- 点击提交: 在 `#cx_imgBg` 上按主图坐标依次 click。
- AI 模型只有在 `vlm.base`、`vlm.key`、`vlm.model` 三项均非空时才算已配置。
  缺少任意一项必须跳过全部 VLM 请求，直接进入工具内人工点击；自动识别多次失败
  后也使用同一人工兜底。人工弹框出现时桌面层会恢复主窗口并发送托盘提醒，避免
  自动任务在隐藏窗口中静默等待。
- 通过判定信号（2026-08-27 修正）: 「获取验证码」按钮进入倒计时/
  变"重新获取"（正则 `\d+\s*[sS秒]|重新获取|重新发送|获取中|已发送|发送中`）
  = 站点已发短信 = 权威通过（站点仅在验证通过后发短信）。**弹窗 #eject
  仍在 ≠ 失败**: 通过后弹窗可能切换到短信步骤而继续存在, 旧版"弹窗仍在=
  未通过"曾把已通过的第一次判失败。弹窗关闭且无倒计时文案 = 按通过处理。
  详见 captcha_handler._wait_result/_sms_sent。
- 指令条获取（2026-08-27 起）: 原生 WebView2 窗口无元素截图, 改 JS 直取
  `.cx_click-tip` 内 3 个目标图标 `<img>` src 下载 2x 放大 (get_tip_icons),
  compose_tip_strip 拼单条供 VLM; 比旧截图裁剪更精确。选择器链
  `.cx_click-tip` > `.cx_tips__answer_div` > `.cx_tips__answer_img` >
  `.cx_tips__answer` (均来自 SDK load.min.js 实测 class)。
  **容器早停陷阱 (17:52 复盘修正)**: SDK 模板常驻多个容器且
  `.cx_click-tip` 默认 display:none 无 img, 「命中第一个存在的容器即返回」
  会导致恒取 0 图; 正确做法是逐容器收集 img 集齐 >=3 才收敛, 并
  重试 6x0.5s 抵御 SDK 异步填充 (get_tip_icons 已按此修正, 兼容
  data:/相对 src)。
  **live 模板为窗口雪碧图 (2026-08-27 18:06 运行日志+site_light.js
  CSS 实锤, 上述采集恒 None)**: 线上弹窗的 3 个指令图标不是 3 张独立
  `<img>`, 而是单张 `<img class="cx_tips__answer_img">` 雪碧图
  (CSS `width:340%; position:absolute; top:-144px`) 透过
  `.cx_tips__answer_div` 84x17 overflow:hidden 窗口显示
  (probe_order3 截图 tip_window.png: 85x17, 图标段 x≈3-16/29-41/
  56-68, 间距约 26px)。get_tip_icons 要求容器内集齐 >=3 张 img,
  单 img 永远不满足 → 返回 None → 双图 PROMPT 从未启用, 全程走
  行1 裁剪单图兜底。**已修复 (2026-08-27)**: get_tip_icons 同步 JS
  返回 `{urls, geom}` (img/容器渲染矩形 + natural 尺寸), 单 img 时由
  `_tip_icons_from_geom` 按窗口∩img 可见交区映射回原图裁切后
  `_slice_strip` 切 3 图标 (3-img 模板 `.cx_tips__answer span img`
  仍优先); 切图失败仍退化行1 裁剪。
- **AI 坐标参考系不稳定（2026-08-27 10 连败样本回放实锤）**: qwen-vl-max
  同一提示词下时而输出 0-1000 归一化坐标、时而按送图 (2x 放大后
  640x480) 像素坐标作答、时而对看不清的图输出近乎重复的空想坐标
  (如三次尝试 [15,340]/[78,340]/[139,340] 与 [48,335]/[79,360]/
  [132,335] 高度雷同)。单一归一化换算把像素帧答案系统性压向原点
  (x 误差达 36%, 图标半径级), 是「点击位置不对」的直接根因。
- **双帧仲裁 + 墨迹验证 (2026-08-27 起)**: 同一份 AI 答案按像素帧
  (x/2, y/2) 与归一化帧 (x*320/1000, y*240/1000) 各换算一次, 只保留
  全点落在主图区的帧, 再经 VALIDATE_JS 页面内墨迹评分仲裁
  (点周围 17x17 patch 内 |灰度-patch中位|>=60 的像素数; 图标上
  40~245, 干净背景 0~20)。验收: 最弱分>=12 且中位>=25 且三点最小
  间距>=18px, 双过取总分高者; 全部不过 = 空想, 不点击直接弃用刷新。
  照片区图标是半透明压印 (混色), 纯白/纯黑阈值连通块会整片漏检
  (10 张样本 0 命中), 墨迹分是唯一稳定判别量。
- **嵌入式 WebView2 不等待 JS Promise (2026-08-27 探针实证)**: 
  `ExecuteScriptAsync` 对同步脚本正常 JSON 返回, 但对 async 脚本
  **不 await**, 返回 Promise 对象的序列化 `'{}'` (脚本抛异常返回
  `'null'`, 与官方 Remarks 一致)。曾致两类事故: ① VALIDATE_JS 等
  async 验证脚本拿不到分数, AI 答案 100% 被误判空想 (一轮 10 连
  弃用); ② `web_flow._api_post` (页内 async fetch) 恒得 `{}`,
  授权/续期接口从未生效, 全靠 DOM 点击兜底 (日志「授权接口失败：
  None」即此表现)。**已修复 (2026-08-27)**: `eval_js` 改"两阶段等待"
  —— 表达式包 async IIFE 结果存页内唯一全局槽 [`ok`,v]/[`err`,msg],
  同步脚本轮询读回 (页内三态 null/['bad']/['v',json] 避双重转义),
  同步/异步表达式统一生效 (真实 WebView2 探针 9/9 通过, 每次调用
  约 +17~72ms)。墨迹验证不回归页内 JS (PIL 复刻更省事)。
  PLAYWRIGHT probe 环境会正常 await (与嵌入行为曾相反), 探针结论
  不能直接推断嵌入行为。
- 顺序源优先级 (2026-08-27 修正): 页面指令条截图 (单图标 2x 放大,
  最清晰) > sprite 行1 裁剪 (2x) > 整图自读 (无指令条兜底)。
  旧逻辑 vlm_solve 内 spot 优先取 crop_row1, 页面指令条永远用不上 —
  已修正。同一张图内部可换顺序源重问 (temperature 0 重问同源
  必复现, 空想答案直接 break 换源)。

## 识别策略（五级，2026-08-28 重构后）

0. **难度预检门控（ASSESS_JS + `assess`）**: 亚秒级页面内分析，难图直接
   刷新换图（刷新免费不耗 attempt，最多 `captcha_gate_max_refresh`
   默认 4 次，耗尽后放行最后一张交 AI）。判难规则（probe_assess
   校准，11 张样本）:
   - 指令行结构异常（行1/行3 分割数 != 3）;
   - 高对比有效图标 < 3（真实图标 contrast=|图标灰度-背景环灰度|
     100~180，同色伪装/噪声块 < 60，阈值 60）; 
   - 低对比块多于有效块;
   - 存在贴边候选（bbox 触碰主图边界，疑似图标被裁切→形状失真
     + AI 点击中心偏移; 实测带贴边候选的样本本地全部失败）。
   预检自身异常时放行（fail-open）。
1. 本地模板匹配诊断（SOLVE_JS + `local_solve`，**不再独立点击**）:
   页面内 JS canvas 解码 sprite。指令行按**单色阈值**分割
   （旧版"纯白或纯黑都算前景"与纯白行背景粘连成巨型连通块，
   是长期 0 命中根因; 现行1 取黑 gray<60、行3 取白 gray>200，
   close + 相邻部件合并至恰好 3 个）; 行1[i] 与行3[i] 同位互检
   （twin IoU>=0.70，实测 0.77~1.0）验证分割质量; 全局最优分配
   （3 目标互斥全排列取总分最高）+ 严格置信（排列内最弱 IoU>=0.45
   且最优/次优排列总分差>=0.06），低置信整体放弃。
   掩码必须用 RGB 三通道判定（灰度会把照片暗彩区误掩进来与图标
   粘连，实测候选从 7 锐减至 3）。
   定位: 历史样本 0/11 命中（排列总分差仅 0.01~0.05）；后续真实样本
   出现两次高置信误点，证明模板分数不能作为直接点击依据。该能力仅供
   `probe_verify.py` 离线诊断，主流程不再调用。
2. 混合方案（当前主解）: `_extract_hybrid_candidates` 用 PIL 对主图区分别
   提取黑、白极性，并对 3x3/5x5/7x7 close 结果按对比度、位置和 bbox
   重叠去重，最多保留 16 个候选。候选图册同时展示原始 RGB 裁图和
   `_normalized_icon_mask` 生成的颜色归一化剪影；原图用于保留照片语义，
   二值图只用于突出轮廓，避免整图二值化把毛发、阴影粘入图标。
   VLM 先为 3 个目标和所有候选给出统一 canonical noun，再返回互斥候选编号；
   本地要求目标名与所选候选名完全一致，并拒绝缺项、重复、越界结果。
   语义通过后以行1/行3黑白模板做水平镜像不变的剪影 IoU 排名门控：所选
   分数至少 0.15，且不低于该目标最佳候选的 85%，否则刷新而不点击。
   坐标始终取候选连通块中心，不由 AI 生成。顺序源为页面指令条
   `get_tip_icons`（权威目标）> sprite 行1/行3规范化目标卡。
3. 端到端 VLM 回退: OpenAI 兼容 chat/completions，sprite 2x 放大 base64
   直发，提示词要求归一化 0-1000 坐标并声明"看不清就回 {\"clicks\":[]}
   不许空想"；temperature 0。答案先过指令区预拦（_strip_answer，全点
   落在指令行带 y[158,240) 的空想形态帧换算前弃用），再双帧换算
   （像素帧/归一化帧）+ PIL 本地墨迹验证仲裁（_ink_scores/_pick_frame，
   与 VALIDATE_JS 同公式, 阈值 MIN_INK=12 / MED_INK=25 /
   MIN_SPREAD=18, 2026-08-27 十连败样本回放校准）。顺序源逐级换源
   重问: 页面指令条 > sprite 行1 裁剪 > 整图自读 (PROMPT 两图模式 /
   PROMPT_FALLBACK 单图模式)。probe 脚本 (page=None) 仍走归一化帧
   旧路径 (不预拦不仲裁)。
4. 失败刷新重试（默认 3 次，每次刷新为新 sprite）+ 人工兑底
   （工具内点击 / 有头模式 beep 等待）。
   可观测性: 每次 attempt 图存 captcha_cache/captcha_时间戳.jpg（保留 10 张），
   AI 回复 content 与 reasoning_content（思考过程，模型支持时）各截断
   400 字符记入日志；接口异常也记日志。

## 纯 CV（不依赖 AI）可行性结论（2026-08-26 系统实验）

实验脚本（保留于根目录）: `probe_rows_crop.py`（四排结构可视化）、
`probe_dualmatch.py`（修正分割 + 黑白双模板互检）、
`probe_chamfer.py`（距离变换匹配，负结果存档）、
`probe_verify.py`（预检+本地匹配离线回归，阈值调参入口）、
`probe_diag.py`（匹配分数矩阵诊断）。

- 修正分割后流程可跑通: 行1 黑阈值分割出 3 模板、主图白/黑掩码
  分割出候选（9/10 样本可用，1 张 strip 非标渲染失败）。
- 但**区分度不足，判定不可行**（作唯一方案）:
  - 二值剪影 IoU（含尺度 ±15%、位移 ±2px 搜索）: 最佳/次佳分差
    仅 0.01~0.1，噪声级；
  - 灰度 NCC: 最佳 0.3~0.6，主图背景差异淹没信号;
  - chamfer 距离变换 + 四渲染（行1~4）融合: 分数全面饱和（0.99+），
    负 gap 频出，完全无区分度；
  - 最干净的证据: 同一图标的黑模板（行1）与白模板（行3）独立匹配，
    9 张样本仅 6 张结论一致——同一图标两次光栅化就翻车，
    说明匹配器工作在噪声底板上。
- 根因: 指令行模板仅 12~20px（约 150~300 像素信息量），而主图图标
  20~45px。模板分辨率是信息瓶颈，任何经典算法都无法凭空补出信息。
  这从机制上解释了早期"手写分割+形状匹配一次通过率约 5%"的结论。
- GitHub 调研参照: taisuii/OpenCV_IconSelect（数美图标点选纯 OpenCV
  识别，84% 成功率）成立的前提是图标 ~75px 均匀渲染、单色、仅简单
  旋转——超星此处 12~20px 模板 + 1.5~2.5 倍尺度差 + 同形干扰项，
  条件不满足，方案不可迁移。ddddocr 此前实测 det 召回约 60% 且
  匹配仍混淆，亦不可行。
- 可落地的折中（已实现）: 二值化只承担多尺度候选召回、颜色归一化展示和
  VLM 结果的形状排名拒错；保留原始 RGB 候选供模型判断。纯 CV 即使达到旧版
  阈值也不再直接点击，避免真实站点已观察到的高置信误点。

## 易错点与结论

- 指令区二值化绝不能"白或黑都算前景"——背景是纯白（致命 bug 根因）。
- 顺序以行1（或行3）为准；行2/行4 是反序干扰行。
  PROMPT_FALLBACK 旧文案曾与实情相反（已修正），改动提示词时
  先对照四排结构再动笔。
- AI 坐标绝不能只信提示词宣称的参考系：qwen-vl-max 归一化/送图像素
  混出。双帧换算 + 墨迹验证是当前唯一可靠仲裁；改阈值先用
  captcha_cache 的失败样本回放校准（墨迹分: 图标 40~245, 背景 0~20）。
- **页内脚本经 eval_js 两阶段桥执行 (2026-08-27 起)**: async 已可用
  (见上文 WebView2 Promise 语义), 但返回值必须可 JSON 编码
  (否则快速返回 None, 与旧行为一致), 悬空不落的 async 脚本最多等
  eval 超时 (默认 30s) 返回 None。重计算类验证仍优先 Python (PIL)
  复刻, 不搬回页内 JS。
- canvas 裁剪必须用 9 参 drawImage 或全图解码后取 y<160: 5 参
  `drawImage(img, 0, 0, W, H)` 是把整张 sprite 压进小画布, 照片区
  纵向压缩 2/3, 墨迹分全假阴性 (17:52 一轮 10 连拒的根因, 回放显示
  其中 5 份答案实际是有效定位)。
- 空想答案特征: 三点墨迹分全低、或三点挤在同一小块 (最小间距
  <18px)、或多次尝试坐标高度雷同 (如 y=340/335 反复出现)。此类
  答案必须弃用刷新, 点击只会消耗 attempt 并触发「失败过多」锁态。
- **单图模式 (PROMPT_FALLBACK) 的典型空想形态 (2026-08-27 10 连败
  回放实锤, 4/10)**: 模型不匹配主图, 而是报**指令行图标自身的
  像素坐标** — 行1 图标在 2x 送图 (640x480) 中位于 y≈320-360,
  故答案呈 y≈330-350 / x≈15-140 且跨图高度雷同。这类答案被
  归一化帧洗白进主图区 (y≈80) 后再被墨迹分拦下; 已实现为
  `_strip_answer` 双参考系预拦 (原始答案全点落在 y[158,240) 指令带
  即弃用, probe 兼容路径保持旧行为)。
- 混合方案坐标精度: 连通块质心/包围盒中心 ±1px，用于点击；
  AI 仅提供语义命名与排序，模型把"猜坐标"排除后失败面明显收窄。
- **Playwright 自测点击兼容 (2026-08-28)**: 内嵌 `PageShim.click` 支持
  `mark=` 以记录人工弹框点击标记，原生 Playwright `Page.click` 不支持该
  参数。`_click_sprite` 已按对象模块区分，仅对 `PageShim` 传 `mark`；此前
  真实自测在点击前抛 `TypeError`，相关轮次不能作为识别准确率样本。
- **当前模型实测边界 (2026-08-28)**: 修复真实点击链路后，以假手机号分别
  执行 10 次和 5 次上限的两轮测试，`qwen-vl-max` 最终 0/2 轮通过。经用户
  授权，运行时配置先切换为官方视觉理解文档平衡档的 `qwen3.7-plus`；首轮
  烟测 1/1 通过。随后为 Qwen3 请求关闭思考、启用 JSON Object 并设置输出
  上限，干净复测 3/3 轮通过，分别消耗 3、2、4 次尝试。该样本说明模型替换
  在当前环境有明显改善，但样本仍小，不能外推为稳定长期通过率。
- **Qwen3 结构化输出约束 (2026-08-28)**: `qwen3.7-plus` 未加结构化约束时，

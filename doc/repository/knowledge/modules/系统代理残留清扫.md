# 系统代理残留清扫

模块: `core/proxy_guard.py` | 接入: `api.py` / `core/windows_desktop.py` / `main.py`
关键词: 系统代理残留, proxy_guard, ProxyEnable, ProxyServer, 脏标记, 开机自检, 关机清扫, WM_QUERYENDSESSION, CloseReason
最后验证: 2026-09-16 | 分支: main

## 职责与边界

CXVPNTools 的原生路由服务负责 system-proxy 接管，以及 TUN 期间的系统代理暂停与快照恢复；
`proxy_guard` 同时提供当前用户的代理读写、无效手动地址修复和 WinINet 刷新辅助。其残留清扫职责为清扫代理工具退出不干净时留在
`HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings` 的
死代理（指向 127.0.0.1 等回环地址、端口无人监听）。不新增系统计划任务，
不修改、不监视第三方工具；PAC/WPAD 型代理不在清扫范围。

## 两条清扫路径

- **启动自检** `startup_check`（`api.start()` 首位调用）：三重条件全部满足才修复——
  ① 脏标记存在（上一轮管理器异常结束）；② ProxyEnable=1 且 ProxyServer 全部条目
  指向回环地址（含 localhost/127.*/::1）；③ 这些端口 TCP 探测无人监听（0.3s 超时）。
  失效场景：第三方工具已重启并重新接管端口时会因 ③ 自动跳过。
- **关机清扫** `shutdown_cleanup`（`DesktopController._on_form_closing` 收到
  `CloseReason` 为 WindowsShutDown/TaskManagerClosing 时经 `on_os_shutdown`
  回调同步执行，main.py 接线到 `api._os_shutdown_cleanup`）：只要 ProxyEnable=1
  且全部条目为回环地址即关闭。**不检查端口监听**——关机时第三方工具进程同样
  即将结束。只做毫秒级注册表操作，不碰网络。

## 状态文件（位于统一用户数据目录）

默认通过 `cfgmod.BASE` 使用 `%LOCALAPPDATA%\CXVPNTools`，不在 exe 目录另建活动副本。
这里的现场快照与原生服务的 `system-proxy-snapshot.json` 不同：后者由接管事务维护并用于自动恢复，
前者只供清扫审计。原生服务的关闭、恢复和 TUN 门控边界见 [代理控制与运行状态](代理控制与运行状态.md)。

- `proxy_guard.json`（脏标记）：`startup_check` 末尾写 `state=running`；
  优雅退出（`api.shutdown()` 末尾与关机清扫成功后）删除。仅系统关机路径
  会在退出前先清扫代理；用户普通点击退出只清标记、不碰代理（第三方工具
  可能仍在运行，用户可能仍需要其代理）。
- `proxy_guard_snapshot.json`（现场快照）：修复前记录 ProxyEnable/ProxyServer/
  ProxyOverride/AutoConfigURL 与 reason（startup_repair/shutdown_cleanup），
  供人工恢复与审计。不做自动回滚：管理器只知道残留现场，无法得知被覆盖前
  的原始设置。
- `proxy-invalid-<时间戳>.json`：无效手动地址修复前的原始字段和 WinINet flags，只供审计；
  不把本来无效的启用状态自动恢复回去。

## 启停期间的无效手动地址修复

- `repair_invalid_manual_proxy` 仅处理 `enable=True` 且去空白后服务器为空或 `:` 的状态，
  不推测公司代理、按协议配置、IPv6 或其它非空地址是否可用，也不探测真实网络。
- 严格读取注册表，查询 LAN 的 WinINet flags，先写 UTF-8 原始快照，再复核注册表四字段及
  flags 未变化，最后通过 `INTERNET_OPTION_PER_CONNECTION_OPTION` 只移除手动代理标志和地址。
  保留 PAC、自动检测和绕过设置；连接名为空，只操作 LAN，不修改命名 RAS/VPN 连接。
- 无效服务器可能令联合 WinINet 查询失败，因此仅查询 `INTERNET_PER_CONN_FLAGS_UI`，
  服务器现场由严格注册表读取确认；备份失败或并发改动时不写入。写后检查注册表与 flags。
- `RoutingManager` 在 TUN 正式启用前、关闭后的当前用户刷新后及复用 standby 前调用修复；
  修复后再次刷新和回读，错误保留在运行日志并中止成功报告。preview 只校验，不执行修复。
- 系统代理读写不具备跨软件原子比较交换；前后核对能发现观察窗口中的变化，不能阻止其它
  进程在检查后再次改写。合法第三方端点仍不在自动修复范围，真实 Windows 交互由用户验证。

## 防误伤规则

- 注册表中存在任何非回环条目（公司/运营商代理）时两条路径都跳过；
  修复动作仅将 ProxyEnable 置 0，不改服务器地址等其余字段。
- 当前单实例互斥（`Local\CXVPNTools.Singleton.v1`）保证自检只跑一次；
  同时持有旧 `Local\CXVPNManager.Singleton.v1` 仅用于阻止新旧版本并行。
- 经理未运行期间第三方工具产生的残留不在本模块职责内，
  它会在"下一次管理器异常关闭后的启动"时才被清扫。

## 用户感知

修复后主窗口不弹出：`DesktopController.notify` 只发托盘气泡
（`request_attention` 是弹窗+气泡，语义不同勿混用）；运行日志带
`[proxy]` 前缀。启动自检在首屏 UI 填充前执行，结果为 None 时无提示。

## 易错点

- 测试里构造 `Api` 骨架并调用 `start()` 时必须给
  `api.proxy_guard.startup_check` 打补丁并准备 `routing_updates` 桩，
  否则会触碰真实注册表并在仓库根目录留下脏标记文件。
- `proxy_guard.py` 的函数全部接受 `registry`/`base`/`port_check` 注入，
  单测不得使用真实 winreg 与真实 BASE。

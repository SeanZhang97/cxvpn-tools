## 控制路径与状态事实

| 操作 | 执行路径 | 成功条件 |
|---|---|---|
| 首页开关 | UI → `set_routing_enabled` → 后端最新保存配置 → `RoutingManager.apply` | 快切或配置事务完成，系统代理写入有回读 |
| 同手动模式换节点 | `save_proxy_preference` → Controller PUT → GET → 保存配置 | `now` 等于目标；保存失败尝试恢复原节点 |
| 改规则、模式、节点组 | 原生服务预检 → 兼容性判断 → Controller 配置热重载或完整事务 | 运行就绪、手动选点、出口验证后 commit |
| 订阅/测速 | 按订阅互斥的网络任务 → 提交阶段短持路由锁 | 配置修订号仍匹配；取消或过期结果不写缓存 |
| 页面读取 | bootstrap → 后台 setup → 版本检查 | 旧请求世代、旧配置修订号不覆盖新结果 |

`running` 表示系统流量接管，`core_running` 表示核心存在；`standby` 可以更新订阅、测速和切手动节点。
已保存配置、原生服务配置、Controller 当前节点是不同事实，不能用保存配置之间的比较证明运行态已经应用。

## 快切与节点偏好

- 快速关闭允许保留完整的 system-proxy 核心并恢复原系统代理，无需联网探测。
- 快速开启除了核心运行、兼容版本和快切标记，还要求控制面最近确认的配置签名与服务 `config_sha256` 一致。
  签名覆盖规范化配置中除 `enabled` 外的字段。新 GUI 进程没有确认记录时，首次开启保守走配置事务。
- 快切开启前回读被引用手动组；与期望节点不符时重新选点并确认，再验证出口和 mixed-port。
- 待机状态的同手动模式选点也会先切核心再保存。组结构或自动策略变化只保存时，下次开启不能走过期快切。
- `remember_selection` 只在变更前完整配置签名与已确认运行配置一致时更新签名，避免把其它尚未应用的偏好一并认定生效。
- 手动 PUT 回读不一致时尝试恢复原节点；恢复不确定、配置写盘失败均不能报告生效。
  切换成功返回确认后的 groups；详情暂不可用时返回 partial 组，前端仅更新选中值并保留节点列表。

## 原生服务、I/O 与事务

当前原生服务版本 `0.7.0`，IPC protocol `6`；`apply` 新增 `allow_reload`，缺省为 false，旧请求不会误走热重载。

- Python Named Pipe 使用重叠 I/O，同一请求的连接、分帧写入与响应读取共用期限。
  status 2 秒、diagnostics 3 秒、普通请求 10 秒、apply 60 秒；连接分别受更短的连接期限限制。
- 服务最多同时处理 8 个连接。连接等待 1 秒、请求帧读取总计 8 秒、响应写入总计 5 秒。
  响应后等待客户端读取确认/断开最多 2 秒，不执行无限 `FlushFileBuffers`。
- 超时先 `CancelIoEx`，取消完成后才释放 OVERLAPPED、缓冲区和事件，避免未完成 I/O 使用已释放内存。
- `begin_prepare` 在短锁内保留准备标识，复制、文件校验和 Mihomo `-t` 在锁外执行。
  准备阶段总期限 45 秒，预检子进程最多 30 秒；超时/取消终止所属子进程。
  Windows 磁盘或 DNS 调用本身不能强制中断，但迟到准备结果必须再次核对标识、取消信号和期限，不能应用。
- 服务关闭或关闭系统代理会取消正在准备的配置。旧准备结果不能清除后续请求的准备标识。
- 只有 `rules`、`mode`、`proxy-groups` 可在其它生成字段完全一致、运行模式一致、核心存活、bypass 文件一致时热重载。
  端口、TUN、DNS、接口、provider 或入口绕过变化会完整重建。
- 热重载事务保留原 data 目录，由 Python 请求 `/configs?force=true`。Controller 重载失败先 rollback，随后最多回退一次完整事务。
  就绪或联网门控失败只回滚，不盲目重复应用。
- `pending.json` 新增 `preserve_data`，旧记录默认 false。热重载回滚不覆盖运行中的 provider 数据；旧格式仍按原边界恢复。
- 删除 pending 记录是原生 commit 点；之后旧备份清理失败只记日志，不将已提交状态报成失败。
  应用失败需确认文件及运行态恢复；恢复失败保留恢复资料并明确报错。
- Python 在任何耗时诊断前先请求 rollback。commit 后记录配置签名不再读取候选文件，成功日志异常不会触发无效回滚。

## 网络任务与快照提交

- `_routing_lock` 继续串行化配置、启停和节点偏好提交；订阅下载、刷新和整组测速不持有它。
- `_routing_provider_task` 在同一订阅内拒绝重复获取/测速，可与其他订阅任务并行；全局测速任务最多 4 个。
- 任务捕获路由配置与修订号；`operation_scope` 将提交 guard 传入调用链，`commit_scope` 只在落盘时获取路由锁（最多等 2 秒）并复核修订号。
  嵌套提交复用已持有的 guard，防止不可重入锁自锁。
- 配置变更前后递增修订号并取消旧测速。旧任务晚到时不写入缓存或节点快照；任务最终回包同样复核版本。
- 运行态订阅更新先确认非空节点组，再在共同提交边界写 provider 正文、元数据和安全节点快照。
- setup 的节点快照对账仍受路由版本 guard 保护；普通配置预检使用独立临时目录，不持路由锁执行扫描与 `-t`。

### 已保存选点模式与待机核心不一致时的节点目录问题

- 当前 `save_proxy_preference` 在系统接管关闭、核心仍待机时，自动/手动模式变更只保存配置，组结构等下次开启时再应用，因此已保存模式与 Controller 组类型可以暂时不同。
- 修复前的 `RoutingManager.proxy_overview` 仅在已保存 provider 满足智能自动策略条件时从 provider 目录枚举节点；其它情况读取公开组的 `all`。若已保存模式切为手动而核心仍保留自动策略组，`all` 实际是内部 `AUTO-…-FALLBACK` 组，可能被误识别为真实节点。
- 修复前的 `refresh_proxy_provider` 和 setup 对账会把上述结果写入安全节点快照，导致节点数量变成内部组数量，并误报原手动节点失效。完整 provider YAML 与 Controller 的 `/providers/proxies` 仍可能保存全部真实节点；不能据展示快照判断远端订阅只返回一个节点。
- `proxy_overview` 现在会递归展开公开组并按 provider 目录补齐真实节点，旧版本已经写入的 `AUTO-…-FALLBACK` 快照会在下一次 setup/订阅读取时被真实节点目录覆盖。排查时仍应分别核对已保存选点模式、公开组类型和成员、目标 provider 的真实节点目录以及本地安全快照；订阅更新成功只证明远端更新完成，不证明旧展示快照已经刷新。
- provider 目录归一化同时过滤策略组对象和 `DIRECT`、`REJECT`、`PHYSICAL` 等内置出口，因此聚合“全部节点”只统计可选订阅节点；订阅说明类条目仍保留给 UI 的流量/到期摘要，并由测速流程排除。

## 订阅下载出口

- `auto` 以订阅 ID、URL 和过滤条件对应的缓存为边界选择首次下载出口。
- 存在缓存时，临时 provider 可通过同 provider 的缓存节点自举；该组保留 `PHYSICAL` 空组回退，
  内置路径没有产出节点后再使用已检测到的 Windows 手动代理。
- 不存在缓存且 Windows 手动代理可用时，首次获取优先使用该代理；失败后尝试物理网络。
  没有 Windows 手动代理时直接以 `PHYSICAL` 下载，不能创建依赖尚未加载 provider 的循环组。
- `physical`、`system-proxy`、`custom-proxy` 是用户显式出口，保持固定语义，不参与 `auto` 重排。
- 临时解析进程总期限为 25 秒；任务日志分别记录所选出口、开始、成功或失败及耗时，且不记录
  完整订阅 URL 或代理凭据。

## 环境与连通性检查

- VPN 与物理网卡扫描并行，TUN 冲突扫描只在 TUN 模式执行。同类环境结果缓存 30 秒，并合并在途扫描；正式应用要求新鲜扫描。
- 环境扫描总体 35 秒；操作系统 DNS 解析总体等待 5 秒；受限后台调用最多 16 个在途线程，避免不可中断系统调用无界增长。
- 出口探测共用 8 秒期限，前两个端点并行，失败后才使用剩余兜底端点。
  每个 HTTP 请求最多 4 秒；成功后不重复探测同一 mixed-port，系统代理仍需注册表回读一致。
- Controller 请求坚持显式直连回环，避免读取 Windows 代理后递归进入自身 mixed-port。

## 测速、调度与前端

- 节点测速默认 8 个 worker，只维持并发窗口大小的已提交请求，整体 120 秒期限。
  取消后不等慢请求结束、不再发布迟到进度；已收集结果与完整原节点列表合并，未完成节点不从快照消失。
- job 含单调 version；`get_routing_test_job(after_version)` 对未变化任务返回 `unchanged`，省去完整节点载荷。
  终态不接收迟到进度，超时有独立失败文案。
- 可见节点页常态 750 ms 轮询；隐藏或离开节点页至少 2 秒，异常按现有策略退避至 5 秒。
- 进度只刷新当前需要的节点/首页区域，不重建订阅表单；节点卡片子内容仅在内容签名变化时重建。
  已结束的历史 job 不会在后续 setup 中重新覆盖新快照。
- setup 使用请求世代与后端 `routing_revision` 双重校验。配置提交、节点偏好和桌面状态流使旧读取失效。
  失效的前台 setup 正确释放其 busy 状态，不清除后续操作的 busy 状态。
- 普通 system-proxy 开关和手动节点点击去除重复确认；初装/升级、TUN、脏草稿和修复等需要解释风险的既有确认保留。
  刷新订阅时首页仍可关闭代理；成功回包立即更新页面，完整 setup 在后台补齐。
- 自动更新按订阅轮转。失败按 60 秒起指数退避、最大 3600 秒，成功至少等待配置 interval；失效订阅和 URL 变化清除旧调度键。
  自动更新仍只在未开启系统接管且订阅主动开启 auto_update 时执行；停止 worker 后旧结果不能提交。

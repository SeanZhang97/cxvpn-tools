# 验证码预检门控与本地双行互检重构

- 日期: 2026-08-26
- 功能名: 图标验证码难度预检门控 + 本地模板匹配修复重构 + AI 提示词结构化
- 分支: 非 Git 工作区

## 背景

离线实测确认 `core/captcha_handler.py` SOLVE_JS 存在致命 bug: 指令区二值化把
"纯白或纯黑"都当前景，而指令区背景本身纯白 → strip 粘成巨型连通块被过滤，
11 张历史样本 0/11 命中，本地层自上线从未生效，全部流量走 AI 层。
结合实验结论（纯 CV 因模板 12~20px 信息瓶颈不可作唯一方案）与验证码
免费刷新机制，本次按"预检门控 + AI 主力"方向重构。

## 关键设计

- **难度预检门控（ASSESS_JS + `assess`，第 0 级）**: 亚秒级页面内分析，
  难图直接刷新换图（不耗 attempt，最多 `captcha_gate_max_refresh` 默认 4 次，
  耗尽后放行最后一张交 AI）。判难规则（probe_assess 校准）:
  - 指令行结构异常: 行1/行3 分割数 != 3（AI 读指令也易错）;
  - 高对比有效图标 < 3: 真实图标 contrast 100~180（iconG≈0-10 或 ≈250），
    同色伪装/噪声块 contrast < 60（iconG 15~50），阈值 60;
  - 低对比块多于有效块: 干扰过重;
  - 存在贴边候选: bbox 触碰主图边界疑似图标被裁切（不完整 → 形状失真
    + AI 点击中心偏移; 实测带贴边候选的样本本地全部失败）。
  预检自身异常时放行（fail-open）。
- **SOLVE_JS 重写（`local_solve`）**: 修复致命 bug——指令行改"单色阈值"
  分割（行1 取黑 gray<60、行3 取白 gray>200，close + 相邻部件合并至 3 个）;
  行1[i] 与行3[i] 同位互检（twin IoU >= 0.70，实测 0.77~1.0）验证分割质量;
  全局最优分配（3 目标互斥全排列取总分最高）+ 严格置信（排列内最弱
  IoU >= 0.45 且最优/次优排列总分差 >= 0.06，低置信整体放弃转 AI）。
- **掩码教训**: 主图候选掩码必须用 RGB 三通道判定——灰度判定会把照片
  背景暗彩区（灰度可 <60）误掩进来与图标粘连，实测候选数从 7 锐减至 3。
- **AI 顺序源三级兜底（`crop_row1`）**: 页面指令条截图 > sprite 行1 裁剪
  （y[158,182) 2x 放大 PNG，行1 即真实点击顺序）> 完整 sprite。
  `vlm_solve`/`hybrid_solve` 均已接入。
- **提示词结构化**: PROMPT/PROMPT_FALLBACK/HYBRID_PROMPT 融入四排结构
  （行1=真顺序、行2=反序、行3 白图标黑底同行1、行4=行3 反序）、颜色反相
  提示（黑模板可能对应主图白图标，按形状匹配）、图标规格（实心带镂空
  20~45px 无旋转）与坐标说明（TOP-PHOTO 区域 y 0..160）;
  修正 PROMPT_FALLBACK 与事实相反的旧行序文案。

## 影响范围与验证

- `core/captcha_handler.py`（SOLVE_JS/ASSESS_JS/local_solve/assess/
  crop_row1/vlm_solve/hybrid_solve/handle_captcha）、`core/config.py`
  （新增 captcha_gate_max_refresh 默认 4）。handle_captcha 对 web_flow/
  test_captcha 的调用签名不变。
- 离线验证（probe_verify.py，11 张历史样本）: 行1/行3 分割 11/11 恰好
  3 个（对比旧版 0/11）; 预检判难 5 张全部对应本地弱匹配失败或非标图，
  判易 6 张失败原因均为"相似图标区分度不足"（AI 语义强项）;
  本地匹配 0/11 命中（排列总分差 0.01~0.05），定位为"极端分明图安全网"，
  AI 为主力路径。
- 待端到端实测: test_captcha.py 复跑记录预检刷新分布与整图通过率。

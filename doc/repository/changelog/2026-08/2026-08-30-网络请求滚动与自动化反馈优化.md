# 网络请求滚动与自动化反馈优化

- 日期：2026-08-30
- 分支：非 Git 工作区
- 功能名：网络请求滚动与自动化反馈优化

## 需求概述

保留个人使用场景下的完整请求和日志内容，修复内嵌浏览器网络请求详情在后台实时刷新时自动滚回顶部的问题，并处理真实自动化检查中发现的低风险交互问题。

## 问题根因

- Worker 每秒推送一次浏览器浮层状态，网络请求列表每次都会清空并重建。
- 原实现只保存外层列表的 `scrollTop`，没有保存展开请求详情自身的滚动位置。
- 验证码等待弹窗固定描述为“手机连接”，与 IMAP 邮箱接收配置不一致。
- 总览五阶段状态以零基索引比较一基步骤，当前阶段存在错位。
- 修复入口会断开全部 VPN 并重启系统服务，但前端没有影响确认。

## 关键设计

- 请求快照内容不变时跳过 DOM 重建；新增或补全响应内容时，以当前可见请求作为外层滚动锚点。
- 按请求标识保存展开详情的独立滚动位置，重建后恢复；列表和详情禁用浏览器默认滚动锚定。
- 请求键继续用于保持展开状态，独立内容签名包含请求体、响应体和错误信息，保证迟到的响应内容仍能刷新。
- 验证码等待文案根据 `CFG.sms.method` 动态显示“邮箱验证码”或“短信验证码”。
- 修复 VPN 前展示会断开全部连接并重启 PolicyAgent、IKEEXT、RasMan 的确认信息。
- 完成提示仅声明软件内状态已同步，不再声称远端页面无需刷新。

## 影响范围

- 内嵌浏览器网络请求抽屉。
- 自动化验证码等待弹窗和总览续期进度。
- 总览 VPN 服务修复入口。
- 不改变网络日志内容、采集范围和复制能力，不实施脱敏。

## 后续修复：手动连接确认状态卡死

### 现场现象与根因

- 17:15:21 `中经云pptp` 提交连接后进入 30 秒 `verifying`。
- 17:15:40 用户又连接 `上地七街IKEV2`，17:15:42 后者已成功连接。
- 新操作调用 `prepare_connection_target` 清除了前一条确认截止时间，但没有覆盖旧的
  `connection_action`；立即成功分支也只清理退避状态，没有写入 `connected`。
- 因确认截止时间已经为零，超时检查不再处理旧动作，界面便长期保留第一条 VPN 的
  “连接确认中”。Windows 实际状态为前者 `Disconnected`、后者 `Connected`。

### 修复设计

- 新的手动连接目标立即写入 `connecting`，覆盖任何旧目标的活动状态。
- 拨号立即成功写入 `connected`，拨号失败写入 `failed`，异步提交继续进入既有
  30 秒 `verifying`。
- 目标本就在线时写入 `connected`；切换模式断开旧 VPN 失败时写入 `failed`。
- 增加“确认期内改连另一条 VPN”的 Worker 回归测试，并补齐并行、切换、已有连接和
  断开失败的 API 状态断言。

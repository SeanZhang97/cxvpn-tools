# 2026-09-28 检查更新网络重试与错误详情

## 日期

2026-09-28

## 功能名

检查更新偶发 URLError：瞬时网络故障自动重试 + 错误文案展示具体原因

## 分支

main

## 问题根因

- 检查更新对 GitHub Releases API 只发单次请求（12 秒超时），无任何重试；
  请求经 urllib 默认系统代理探测，VPN/代理启停切换瞬间容易出现连接重置、
  超时等瞬时故障，直接以失败告终，表现为偶发"检查更新失败：URLError"。
- 失败文案只含异常类型名（URLError），不含具体原因（超时、连接拒绝等），
  用户和排查都无法区分是 DNS、代理还是超时问题。
- 第一轮修复上线后实测复现：系统代理指向本应用自己的 Mihomo 混合端口
  （127.0.0.1:17890），Mihomo 对 `api.github.com:443` 的 CONNECT 隧道返回
  400 Bad Request。此类"代理隧道被拒"重试同一代理无意义，必须换路由。

## 修复动作

- `core/app_update.py` 新增 `_request_with_retry`：网络层错误（URLError 及
  OSError 家族）最多尝试 3 次，间隔 1s/2s（`CHECK_MAX_ATTEMPTS`、
  `CHECK_RETRY_BACKOFF`）；HTTPError 属于服务端明确答复，不重试。
  版本检查和 `.sha256` 校验附件下载均走重试。
- 同一函数增加直连兜底：最后一次尝试使用
  `urllib.request.build_opener(urllib.request.ProxyHandler({}))` 显式禁用
  系统/环境代理（与 `core/routing.py` Controller 请求的既有模式一致）；
  检测到 Tunnel connection failed 时立即转入直连兜底，不再重试同一代理。
  直连也失败时，界面展示直连的错误原因。
- 新增 `_describe_network_error`：失败文案变为
  `检查更新失败：URLError（timed out）` 形式，单行、截断 120 字符，
  不含更新服务地址等实现细节。
- 重试事件与最终失败详情写入运行日志（经 `api.check_app_update` 传入的
  log 回调），失败日志带 manual 标记与具体原因。

## 注意事项

- 最坏情况下一次手动检查约需 42 秒（3 次 × 12 秒超时 + 3 秒退避），UI 有
  "检查中…" 忙碌态；自动检查在后台执行，无感。
- HTTP 5xx 目前不重试，如后续观察到 GitHub 侧瞬时 5xx 可再评估。
- Mihomo 对 api.github.com 的 CONNECT 返回 400 属代理路由侧问题
  （节点/规则/上游），本次未展开；如直连兜底也不可用，需单独排查代理链路。

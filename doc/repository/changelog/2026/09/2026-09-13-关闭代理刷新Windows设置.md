# 关闭代理刷新 Windows 设置

- 日期：2026-09-13
- 功能：关闭系统代理后刷新 Windows 设置页
- 分支：main

## 问题与定位

首轮将问题归因于用户会话刷新不足，补充通知后用户复测仍出现空白卡片，故该判断不能作为根因。
随后只读对比发现：system-proxy 开启时 `ProxyEnable=1`、地址为本机 mixed-port；切换 TUN 后
服务报告 `system_proxy_active=false`，但注册表恢复为 `ProxyEnable=1`、`ProxyServer=:`。
原恢复逻辑不校验快照地址，因此把无效的启用状态重新写回 Windows。该异常与设置页和浏览器
故障相关，具体界面与网络恢复结果仍需用户验证，不能用服务状态或离线测试代替。

## 变更

- 原生服务成功关闭系统代理或停止系统流量接管后，GUI 在当前登录用户会话重新调用
  `INTERNET_OPTION_SETTINGS_CHANGED` 和 `INTERNET_OPTION_REFRESH`。
- 通过单窗口超时 1 秒（非广播总期限）的 `WM_SETTINGCHANGE` 广播通知已打开的 Windows 设置窗口重新读取
  `Internet Settings`。
- 补充请求、成功、部分失败和耗时日志。刷新失败不回滚已成功完成的代理关闭事务。
- 原生恢复逻辑对缺失、空白或仅为冒号的服务器地址做有限归一化，不重新开启无效手动代理。
  正常企业代理、按协议代理、IPv6、绕过列表和 PAC 保持原值；本来缺失的字段保持缺失。
- 修改异常快照前另存原始 JSON，备份失败不写注册表；恢复后逐项回读四个字段，全部一致才
  删除活动快照。失败保留恢复资料，记录恢复阶段与结果。

## TUN 系统代理事务修复方案

调用链为 `RoutingManager.apply` → `_install` → 原生服务 `apply_prepared` → TUN 运行时启动 →
系统代理处理 → Python 运行态与出口确认 → `commit`/`rollback`。原逻辑把“TUN active”和
“停止接管”都归入 `restore`，因此切换、服务重启及回滚恢复到旧 TUN 时，都可能在 TUN 仍运行的
情况下重新启用快照中的手动代理。

- TUN active 改为独立的 suspend 语义：先保存用户原始代理快照，再关闭手动代理和 PAC、刷新
  WinINET，并逐项回读；成功后保留快照，不在 TUN 运行期间恢复。
- 运行配置记录本软件管理的 mixed-port。若历史快照把当前本机端口误存为“原始代理”，先保留
  审计备份，再把长期恢复目标归一化为关闭状态，避免以后停止 TUN 时重新制造残留。
- TUN 停止、运行时熔断或明确关闭统一分流时继续恢复原始快照；事务失败恢复旧 system-proxy 时
  重新激活旧端口，恢复旧 TUN 时重新执行 suspend，保持失败前接管语义。
- Python 控制面在候选事务提交前再次读取当前用户的 `ProxyEnable`、`ProxyServer` 和刷新结果；
  仍未关闭时触发原生 rollback，不以绕过系统代理的 TUN 连通性探测代替该确认。

成功标准：TUN 候选事务提交前手动代理启用位关闭且服务器地址为空；TUN 重启与回滚后保持相同
语义；停止 TUN 后恢复进入接管前的合法设置；任何写入或回读失败均不提交候选配置。

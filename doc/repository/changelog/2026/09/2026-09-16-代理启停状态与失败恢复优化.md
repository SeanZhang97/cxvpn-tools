# 代理启停状态与失败恢复优化

- 日期：2026-09-16
- 分支：main
- 功能：代理启停、原样保存、失败识别与恢复
- 方案：[代理启停状态收敛方案](../../../plans/2026-09-16-代理启停状态收敛方案.md)

## 问题与范围

真实日志与历史配置确认：TUN 关闭后出现已开启但地址为 `:` 的 Windows 手动代理；
原样保存配置仍重建待机核心；候选 Mihomo 已退出，上层仍等到 Controller 超时，回滚后的
日志末尾又覆盖失败现场。不能据此确定无效地址的写入来源或当次 Mihomo 退出的底层原因。

用户授权优化并由子智能体审查，明确不执行真实代理启停，最终由用户手动验证。
优化阶段只修改源码和文档；用户随后明确要求打包重启，已按项目规则构建并重启 GUI。
未手动执行真实代理启停或安装/重启原生服务，实际启停与网络验收仍由用户完成。

## 关键改动

- 正式 TUN 启用前及关闭后严格核对 Windows 手动代理；仅对启用的空地址/冒号，先备份和
  复核，再通过当前用户 WinINet LAN 设置关闭手动代理并清空端点。保留合法第三方代理、
  PAC、自动检测、绕过列表与命名 RAS 连接；preview 不修改系统设置。
- 原样保存关闭配置时，兼容、签名一致、无 pending/熔断/系统代理活动快照且 Controller
  可读的 standby 直接复用。已停止核心仍保留幂等清理，避免漏掉上次失败的路由/快照恢复。
- 等待 Controller 与订阅组时检查核心是否仍运行；异常退出立即失败。原生 status 不吞退出
  证据，日志记录 PID/退出码，commit 再次确认核心存活，失败保留回滚材料。
- 在候选失败或 rollback 前保存脱敏日志，沿用既有 diagnostics 字段，下一 apply 清理；
  日志读取上限 64 KiB、保留末尾 30 行。诊断不延迟必要回滚。
- 快切只允许兼容且无 pending 的核心；补写启用位前确认仍为本机目标端口。原生快切部分
  失败按原模式恢复实际代理状态；回退失败、自动 rollback 失败准确报告。
- 停止时删除启用标记失败直接报错并保留运行态；标记已清除后的模式清理、核心停止和代理
  恢复分别尽力执行并汇总错误，避免报告成功后被残留启用标记重新拉起。
- 启动系统代理对账统一经过 apply 的配置/自动网卡门控；提交后的缓存维护失败不再误报
  配置失败或漏调度待机恢复。

## 子智能体审查

两位子智能体分别审查 Python 与 Rust 启停逻辑。已纳入快切补写边界、快切部分失败恢复、
status 吞退出事件、commit 存活复核、停止标记失败、启动对账绕过门控与提交后维护异常问题。
复核发现的“stopped 即跳过清理”风险已收回该优化；不扩大或改变既有 TUN 自动恢复策略。

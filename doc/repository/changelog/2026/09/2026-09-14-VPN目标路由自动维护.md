# VPN 目标路由自动维护

- 日期：2026-09-14
- 分支：main
- 状态：功能实现与本地验证完成，真实网页验收受 Windows VPN 会话异常阻断。

## 需求与根因

域名后缀规则已经覆盖新子域名，Mihomo 也会动态解析 DNS；缺失的是 Windows 分流 VPN
到真实目标地址的路由。只绑定出口接口无法覆盖没有静态路由的新服务器 IP。
用户已批准 [实现方案](../../../plans/2026-09-14-VPN目标路由自动维护方案.md)。

## 实际改动

- 固定 v1.19.30 核心增加受管 VPN 的连接前钩子：沿用实际 DNS 结果，TCP/UDP 发包前
  申请精确 `/32`、`/128` 活动路由，无需枚举子域名或重连 VPN。
- 独立受限 Named Pipe 与原生 IP Helper 管理器，仅接受当前核心进程、世代和所选 VPN。
  不接收任意网关、网段、metric 或命令；设置超时、容量限制和取消补偿。
- 目标路由与 TUN/物理保护路由配对，验证未绑定流量仍经原接管接口。已有用户路由仅复用，
  不认领、不删除，也不新增全局默认路由。
- 租约共享、连接结束后 60 秒回收、持久恢复意图、严格所有权检查、清理失败保留保护路由；
  服务异常退出通过 Windows Job 结束核心，下一次启动恢复记录。
- 核验真实 VPN 接口和可用 IPv6 地址，拒绝 fake-IP 等无效目标；不可用时保持明确失败。
- 服务升级至 0.8.0、控制 IPC 7；核心能力门控，升级失败成对恢复旧服务及旧核心。
- 核心版本、上游源码、补丁及二进制摘要锁定；随包提供修改后对应源码与 GPL 说明。
  普通 direct 的自定义字段为可选，避免影响物理和上游直连配置。

## 验证结果

- Python 73 项相关离线测试通过，隔离用户数据、网络、进程和服务调用。
- Rust 38 项离线测试通过；1 项原生路由测试默认 ignored，另行显式运行后通过。
- Go 4 项相关测试通过：冷请求/取消、并发、UDP 目标变化、普通与受管 direct 解析兼容。
- 原生 API 在保留测试地址上完成创建、回读和删除；测试路由已清理。
  原型验证 TUN 和 system-proxy 的保护接口选择，不代表完整双模式端到端回归。
- 实际服务升级、配置事务提交、核心能力回读成功；用户主库配置未改变。
  TUN 对 gstatic 和 Cloudflare 两项系统链路检查均返回 204。
- 首次请求 mooc/mooc1 后自动出现 VPN 精确路由及 TUN 保护路由；连接失败后释放并自动清理。
- 非核心进程直接申请路由被实际 Named Pipe 拒绝。
- 实际 HTTPS 未通过：Windows RAS 返回连接成功但没有有效 VPN 网卡；关闭 TUN 再连接仍重现。
  已恢复 TUN，没有把路由创建成功等同于业务网页验收。
- 未进行真实 IPv6、服务强制崩溃和完整多 VPN 端到端回归；相关离线测试仅覆盖部分边界。

## 交付与注意事项

- 使用 `uv run --with pyinstaller python build.py` 打包成功，17:04 自动启动
  `dist/CXVPNTools/CXVPNTools.exe`；确认进程存在，主库 revision 96 未变。
- 分发包的核心、原生服务、对应源码包和构建清单摘要均与验证产物一致；
  包内未发现用户主库、兼容配置、owner SID 或路由恢复记录；最终 TUN 连通性检查返回 204。
- 主库和兼容 JSON 由打包生命周期备份及核对，用户原有 6 条 office host route 与
  `45.113.20.0/24` 不属于动态管理器所有权，已核对保留在 VPN 配置中。
- 当前网络阻断需恢复 Windows VPN 的有效会话后再次验证，不能宣称原链接现已恢复。
- 定制核心升级必须重放固定补丁、回归并更新摘要；日常打包仅核对一致性。

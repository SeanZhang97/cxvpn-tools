# 自动升级守护启动修复

- 日期：2026-10-10
- 功能：修复升级守护未执行即退出，补发 v1.3.3
- 分支：main

## 问题根因

- 用户在另一台电脑从 v1.3.1 升级 v1.3.2：安装包下载及 SHA-256 校验成功，守护进程三次均在首轮监控前以 0 退出，没有结果文件，也没有 UAC 窗口。
- 用户提供的守护脚本与仓库生成内容完全一致；直接运行 Windows PowerShell 的只读命令正常。
- 原生产入口同时使用 `DETACHED_PROCESS`、`CREATE_NEW_PROCESS_GROUP`、`CREATE_NO_WINDOW`，标准流均指向空设备。本机以同一脚本及参数复现退出码 0、脚本不执行且不生成结果文件。
- 去掉 `DETACHED_PROCESS` 后正常执行脚本和状态写入；Windows PowerShell 应使用无窗口进程及独立进程组。
- 开发工具可能传入 PowerShell 7 的 `PSMODULEPATH`，导致 Windows PowerShell 找不到 `Get-FileHash`；升级子进程移除该继承变量，由 Windows PowerShell 生成默认模块路径。

## 涉及文件与设计

- `core/app_update.py`：移除不兼容的分离控制台标志；保留无窗口与独立进程组，清理升级子进程的模块路径继承。
- `tests/test_app_update_hardening.py`：真实生产启动路径回归，使用临时 Unicode 目录和被改变的公开测试文件，确认守护执行并在 UAC 前写入校验失败；保留成功、重启、取消、超时和启动失败夹具。
- 夹具提前加载 Utility 模块，防止自定义 `Get-Item` / `Test-Path` 替身阻断模块自动加载而产生误报。
- `core/version.py`：版本更新为 1.3.3，Windows 文件版本同步。
- `doc/repository/knowledge/common/打包与分发.md`、月份索引和本记录。

## 影响范围

- 仅调整升级守护的进程启动方式与子进程环境，不改变下载校验、UAC、安装器依赖处理、结果判定或用户数据迁移。
- 仍由守护等待安装器真实退出，再核对注册表、EXE 版本及精确进程；超时不强杀安装器。
- 旧 v1.3.1/v1.3.2 客户端在安装新包前仍使用旧升级器；遇到此故障应手动运行 v1.3.3 安装包一次，保留原安装目录，无需卸载。

## 验证与交付

- 59 项升级下载、API 状态及守护相关离线测试通过。
- 真实生产 `launch_installer` 的无窗口启动、UTF-8 状态文件和 Unicode 路径回归通过；错误摘要阻止 UAC 与安装器调用，未安装真实软件或修改真实用户库。
- 本机复现及测试并不等于已经在另一台电脑完成真实安装升级；该机器需手动安装后的实际验证。
- 受保护构建、配置核对、重启与 Release 资产检查在交付阶段补充。

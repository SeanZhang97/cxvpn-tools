# 订阅代理回退与测速对齐

- 日期：2026-09-01
- 功能名：订阅首份节点自动引导与节点延迟口径对齐
- 分支：main

## 需求概述

修复首次没有节点缓存、订阅地址又无法物理直连时，默认更新流程直接失败的问题；确认并
固化“测速只测试当前缓存节点、不重新拉取订阅”的行为，同时缩小与 Clash Verge Rev 的
延迟数值差异。

## 问题根因

- 原 `auto` 下载出口只在同一订阅已有缓存时复用缓存节点，否则回退到 `PHYSICAL`。首次无
  缓存且订阅需要代理时，没有继续复用当前 Windows 手动系统代理。
- Clash Verge Rev v2.5.2 的手动更新会在常规更新失败后继续尝试自身本地代理和 Windows
  系统代理，因此相同网络条件下能完成首份节点引导。
- CXVPN 与 Clash 默认使用不同测速目标：CXVPN 使用 Google HTTPS，Clash 使用 Cloudflare
  HTTP。目标地理位置、链路和 TLS 握手差异会让同一节点出现明显不同的延迟。

## 关键设计

- 保留 `auto` 的内置缓存节点和物理网络主路径；只有主路径没有产出节点、当前不是 YAML
  导入或纯缓存测速，并且检测到 Windows 手动系统代理时，才自动以显式 `system-proxy`
  重试一次。
- 自动回退不改写订阅的 `download_route`；成功结果显示实际使用的系统代理回退出口，失败
  时给出覆盖三条路径的可操作提示，日志记录开始、成功、失败、耗时和异常类型，不记录订阅
  URL 或代理凭据。
- 临时节点测速继续使用 URL 指纹匹配的 last-known-good 文件 provider；配置不含订阅 URL，
  Controller 调用不发送 provider `PUT`，因此不会在测速时刷新订阅。
- 默认健康检查和节点测速目标改为 Clash Verge Rev v2.5.2 的
  `http://cp.cloudflare.com/generate_204`。节点 API 仍要求 HTTP 204，单节点超时 10 秒，批量
  测速最多 8 路并发。
- 订阅出口 UI 改为“智能自动更新”，说明实际尝试顺序；失败恢复提示不再要求用户先手动切换
  到系统代理。

### 后续优化：关闭代理后的常驻节点核心

- 将原生路由服务升级到 `0.3.0`、IPC 协议升级到 `3`，新增持久化的
  `active/standby/stopped` 三态。关闭代理只停止 TUN/Windows 系统代理接管，已有启用订阅时
  随后启动仅绑定回环地址的待机 Mihomo；待机核心不接管系统流量。
- 关闭流程先执行 `stop_runtime` 并恢复 Windows 原始路由，再事务启动待机核心。待机配置、端口
  或 provider 校验失败时保持代理关闭，仅返回可见警告并降级到临时核心，禁止回滚成接管状态。
- 待机配置加载全部已启用 provider，保留 Controller 和 `mixed-port`，让已有缓存节点能够为
  同一 provider 的远端更新提供代理出口；节点测速继续只调用当前核心 Controller，不下载订阅。
- 新增受 SID ACL 保护的 `read_provider` IPC。常驻核心更新成功后，把 ProgramData 中的完整
  provider YAML 同步到当前用户 last-known-good，避免下次临时测速或服务重装读取旧缓存。
- 后端状态新增 `core_running`、`standby`、`runtime_mode`；`running` 只表示系统流量接管真实生效。
  UI 明确显示“代理接管中”或“节点核心待机”，并区分 `remote_updated`、`cache_retained`、
  `cache_tested`、`cache_imported` 四种结果。
- GUI 关闭期间的自动更新优先复用待机核心；服务未安装或待机不可用时继续使用临时核心，不改变
  首次无完整节点缓存且无任何可用外部出口时必须导入 YAML 或恢复代理的边界。

### 后续优化：代理启动、测速与首页加载解耦

- 对照 Clash Verge Rev `v2.5.2`（commit `28f2efc`）确认：系统代理/TUN 开关与节点
  delay/healthcheck 是独立调用链，节点测速不作为启用前置条件。CXVPN 启动时不再重复执行两次
  provider healthcheck，只确认运行代理组与当前选点一致，最终仍以 TUN 或 Windows 系统代理的
  真实端到端链路探测作为提交门控；失败继续事务回滚并恢复 Windows 原始路由。
- 网络代理导航改为先使用已加载快照同步渲染，再以后台模式补齐完整 setup。15 秒缓存过期后进入
  首页不再触发全局 `busy` 并锁住“开启代理”；首次完全没有快照时仍只等待快速 bootstrap。
- 从 Mihomo 节点 history 提取 `tested_at`，首页延迟同时显示测速时效，并区分未测速、历史测速、
  测速不可用与待启用，避免把历史 `91 ms` 误读为当前启动一定可用。
- 启动失败使用首页常驻 `role=alert` 承载完整可操作提示；首页可见时不再弹出同内容长 toast。
  UI 只描述已验证失败、已恢复动作和下一步，重试次数、端点分类及“并非某原因”等排查细节只写日志。

### 回归修复：关闭代理更新与失败保留节点

- 修复“重新获取订阅”始终走临时预览、没有优先使用已运行待机核心的问题。已保存、启用且核心
  正在运行时改为先调用常驻 provider `PUT`，关闭 Windows 系统代理/TUN 后仍可复用当前缓存节点
  更新订阅；常驻更新失败再尝试临时备用路径，草稿或核心未运行时直接使用临时预览。
- 修复预览失败分支主动删除 `providerPreviews`，导致磁盘仍有 72 条缓存但节点工作台显示 0 条的
  回归。失败现在只记录错误并保留上次预览、运行组、节点快照和可用数；常驻更新失败同样明确提示
  已保留当前列表。
- 修复临时 provider `PUT` 发出后立即设置 `refreshed=true` 的错误。只有 PUT 成功且回读到非空
  节点才标记远端更新成功；失败时返回 `cache_retained`。
- 当内置代理、物理网络和已检测的 Windows 系统代理都未产出节点时，若完整 last-known-good
  仍存在，则以不联网的 `file` provider 显式恢复节点，并合并原安全快照中的历史测速状态；该
  降级不改写缓存和快照。

## 影响范围

- 影响独立订阅预览、GUI 关闭服务时的后台订阅更新、运行配置中的健康检查目标，以及预览态、
  运行态节点测速。
- 显式 `physical`、`system-proxy`、`custom-proxy` 的固定语义不变。
- 自动回退只复用 Windows 当前已经启用的手动代理，不执行 PAC/WPAD，不扫描常见代理端口。

## 注意事项

- 离线桩与受控真实请求均未输出真实订阅 URL；真实请求不持久化订阅正文或节点快照。
- 若 Windows 系统代理指向不可用端口，自动回退会在有界超时后失败，并保留原有缓存。

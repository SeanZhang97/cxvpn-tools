# 代理控制可靠性与响应优化

- 日期：2026-09-06
- 功能：网络代理、订阅、节点与规则控制逻辑
- 分支：main（保留工作区已有未提交改动）

## 需求与根因

用户反馈开关代理慢、节点切换不顺畅，要求优化此前审计发现的全部问题。

审计发现：管道读写和原生预检缺少完成期限；慢订阅/测速长持路由锁；待机偏好与运行配置不一致仍走快切；
手动选点缺少准确回读和保存回滚；旧 setup 覆盖新操作；重复环境扫描、出口探测及全量重启；
高频完整测速回包和 DOM 重建；首个失败订阅长期占据更新调度。

后续真实日志进一步确认首次订阅更新的慢路径：`auto` 在没有任何节点缓存时仍让订阅下载组
引用同一个尚未加载的 provider，临时核心等待 25 秒仍无节点，之后 Windows 系统代理回退仅需
2.1 秒；总耗时因此达到 27.39 秒。

## 关键设计

1. 使用 Windows 重叠 I/O，将连接和帧读写纳入共同期限；服务连接并发有界，预检在状态锁外执行，
   取消/超时先终止所属操作，旧准备结果不能提交到后续事务。
2. 网络获取和测速不长持路由锁。同订阅互斥，提交缓存/快照时复核路由修订号；
   配置变更和 worker 停止会拒绝旧任务写入，嵌套提交不会自锁。
3. 快切开启同时校验最近确认的运行配置签名与服务配置哈希；待机同手动模式先切点再保存。
   PUT 后必须回读等于目标；切换失败或保存失败恢复原偏好/运行节点，不能虚报成功。
4. 普通手动节点点击和 system-proxy 开关减少重复确认；成功状态立即应用，完整环境详情后台补齐。
   前端用请求世代和后端修订号拒绝旧回包；订阅刷新不再禁用首页关闭代理按钮。
5. VPN/网卡并行扫描并短时缓存，TUN 扫描按需执行；DNS 和出口探测有共同期限，避免逐端点累加等待。
   已验证 mixed-port 后只回读系统代理配置，不重复同一联网探测。
6. 服务版本升至 0.7.0 / protocol 6。规则、模式和节点组变化在兼容条件下热重载；
   端口、DNS、TUN、provider、接口或入口绕过变化仍完整应用。
   热重载失败先回滚，再最多回退一次完整事务；旧 pending 记录保持恢复兼容。
7. 测速只维持并发窗口，取消不等慢请求，120 秒总体期限；job version 跳过未变化回包。
   可见页轮询 750 ms、后台至少 2 秒；进度不重建订阅表单，卡片子内容按变化更新。
8. 自动更新按订阅轮转，失败 60 秒起指数退避、最长 3600 秒；失败订阅不阻塞其它到期订阅。
9. `auto` 首次获取会检查 URL 指纹对应的缓存。没有缓存且检测到 Windows 手动代理时优先使用
   该代理；该路径失败后再尝试物理网络。没有系统代理时直接使用 `PHYSICAL`，不再创建依赖空
   provider 的自举组；已有缓存仍保留缓存节点自举及后续 Windows 代理回退。

原生事务同时修正提交点及恢复结果语义：commit 后旧备份清理失败只记日志；候选应用失败需确认
旧文件、进程及系统代理恢复，恢复失败明确报错并保留恢复资料。Python 在诊断之前执行 rollback，
避免诊断失败或控制台编码异常阻止资源恢复。

## 影响范围与兼容性

- 未更换框架或新增核心依赖；只启用已有 windows-sys 的 Threading feature。
- routing schema、订阅及手动节点持久化格式保持现有定义；运行签名只保存在当前控制面内存。
  首次启动 GUI 没有确认签名时，第一次开启保守走完整配置事务。
- 新增可选回包字段 `routing_revision`、job `version`；新增 `allow_reload` 请求字段在原生端缺省 false。
- `pending.json.preserve_data` 缺省 false，兼容旧事务恢复；热重载保持 live data，不覆盖 provider 运行缓存。
- 完整配置提交仍串行；系统服务、文件系统或外部 HTTP 故障仍可能产生有界等待，并不保证所有操作瞬时完成。
- 首次订阅的出口顺序根据同 URL 缓存和 Windows 手动代理状态决定；不改变用户显式选择的
  `physical`、`system-proxy` 或 `custom-proxy` 路径。
- 工作区原有数据目录迁移、订阅地址显示、打包脚本和其它改动均保留，并随本次现有工作区打包。

# 代理启停等待优化

- 日期：2026-09-01
- 功能名：网络代理关闭等待优化
- 分支：main

## 问题根因

- 用户关闭代理时，系统接管通常已在约 1 秒内停止，但控制面随后同步启动节点待机核心；
  待机启动失败时 UI 会一直等待 Controller 的 25 秒上限，表现为“正在关闭代理”长时间不结束。
- Controller 请求使用 `urllib.request.urlopen` 的默认 opener。Windows 系统代理恢复原值后，
  默认 opener 可能继续把 `127.0.0.1:<controller-port>` 请求送入旧 mixed-port；Mihomo 日志可见
  本地 Controller 目标错误命中 `PROXY`，导致就绪检查超时。

## 关键设计

- 所有本地 Controller HTTP 请求使用空 `ProxyHandler` 创建独立 opener，明确绕过 Windows
  系统代理和进程环境代理，避免回环请求进入 Mihomo mixed-port。
- 快切不可用的关闭路径只同步等待原生服务停止运行时、恢复 Windows 系统代理及配置落盘；存在
  已启用订阅时，返回内部 `standby_pending` 标记，由 API 在保存成功后提交后台待机复核任务。
- 后台待机复核复用 `_routing_lock`。用户关闭后立即重新开启时，新操作与待机事务仍串行执行，
  后台任务取得锁后会重新读取最新配置；若代理已经开启则安全跳过。
- `standby_pending` 只用于后端调度，返回 UI 前移除，不扩展公共配置结构。
- 日志区分任务提交、后台领取、等待互斥锁、开始执行和终态，便于后续定位等待发生在哪一层。
- 原生服务升级为 v0.4.0 / IPC protocol v4，增加 `set_system_proxy_enabled`：完整配置已加载且
  `fast-toggle-ready` 标记存在时，只切换 Windows 系统代理快照和 `active/standby` 模式，Mihomo
  子进程、Controller、provider、规则和 DNS 均保持常驻。
- 控制面仅在请求配置与已保存配置除 `enabled` 外完全一致时允许快路径；系统代理模式、原生服务、
  常驻核心、快切标记和非熔断状态缺一不可。配置、节点策略、规则、DNS 或流量模式变化时继续执行
  完整预检、候选事务和回滚，不因快开关降低配置变更的安全门控。
- 快速开启前保留一次真实 mixed-port 端到端验证和当前代理组确认；通过后写入并回读 Windows
  系统代理，不再重复执行 VPN/网卡/TUN 扫描、Mihomo `-t`、核心重启和第二次等价公网检查。
- 系统代理关闭态的待机配置改为完整可运行配置。首次迁移、配置变更或快切标记缺失时，后台事务
  重建完整待机核心；普通关闭只恢复 Windows 系统代理，核心不重启。
- 首页新增仅修改 `enabled` 的后端入口，始终基于后端最新配置提交，避免前端旧快照覆盖其它字段。
  前端收到应用结果后立即更新本地状态并解除按钮，完整 `get_routing_setup` 改为后台刷新，不再在
  开关前后各阻塞一次 VPN、网卡和 TUN 扫描。
- 性能路径不作为界面卖点：按钮、确认框和结果提示统一使用普通“开启/关闭”表述，快切路径信息
  仅保留在内部状态与诊断日志中。

## 影响范围

- Windows 系统代理关闭完成后不再被待机核心的配置预检、Controller 等待或失败回滚阻塞。
- 待机核心能力仍保留；后台失败时代理保持关闭，订阅更新和测速继续使用原有临时核心降级路径。
- 开启代理原有的环境校验、Mihomo 预检和端到端网络门控保持不变。
- 普通系统代理启停在配置未变化时使用快路径；TUN、配置变化、服务升级未迁移完成和异常恢复仍走
  完整事务，耗时与原流程一致。
